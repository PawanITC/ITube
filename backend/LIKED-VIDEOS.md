# Liked videos: beginner walkthrough

## What the feature does

A signed-in user can like a video, unlike it, check whether they liked it, and view
their liked videos. The frontend provides a Like button on the watch page and a
Liked videos library page at `/liked-videos` (the older `/#liked-videos` link also works).
It uses real accounts, videos, sessions, and the team's PostgreSQL setup. There are
no hardcoded user IDs or seeded video likes in the production code.

## 1. Decide the rules before writing code

Start with behavior, not class names. We agreed on these rules:

- A user can like a video only once. Many users can like the same video.
- Repeating Like leaves the existing entry and its original time unchanged.
- Repeating Unlike succeeds even if there is no entry. Unlike removes the like,
  never the video. Liking again afterward creates a new time.
- The server obtains the user ID from the session. A client cannot choose another
  user's identity by adding `?userId=...` to the URL.
- Videos must exist to be liked or queried for status. A private video is available
  only to its channel owner. Users may still remove an old like after privacy changes.
- Members-only videos can be liked without buying membership; liking does not grant
  playback access. The existing player still obtains playback authorisation.
- Lists show most recently liked first and are paginated. When times match, the
  higher like-record ID comes first for a consistent ordering.

Before starting, inspect the existing `AccountEntity`, `VideoEntity`, `CurrentUser`,
`VideoSummaryDto`, SQL initialization, package layout, and frontend routing. This
prevents creating duplicate user/video models or incompatible conventions. Java 21,
Spring Web MVC, Spring Data JPA, validation, PostgreSQL, React, and the team's session
infrastructure were already present; the feature needs no new dependencies.

## 2. Design the database

`src/main/resources/schema-liked-videos.sql` defines `liked_video`:

| Column | Meaning |
| --- | --- |
| `liked_video_id` | Unique identity of this like record; generated by the database |
| `user_id` | Which existing account liked the video |
| `video_id` | Which existing video was liked |
| `liked_at` | When the server recorded the like |

Do not confuse the like-record ID with the video ID. Our public endpoints use the
**video ID**, because the viewer clicks Like on a video and should not need to know
the database ID of the relationship.

The foreign keys reference `accounts(user_id)` and `video(video_id)`. They prevent
references to records that do not exist. PostgreSQL's `ON DELETE CASCADE` removes
associated likes when an account or video is deleted.

`UNIQUE (user_id, video_id)` protects the one-like-per-user-per-video rule at database
level. Checking in Java alone would be insufficient: two simultaneous requests could
both check before either one saves. The unique constraint plus the conflict-safe
insert handles this situation.

The index on `(user_id, liked_at DESC, liked_video_id DESC)` supports reading a user's
likes in the order we need. The script is added after the account/video schema in
`spring.sql.init.schema-locations`. This app currently uses idempotent SQL startup
scripts and Hibernate validation; we follow that approach rather than introduce
a separate migration tool. A future team migration should move this schema along
with the other tables.

## 3. Map the table to an entity

`entities/LikedVideoEntity.java` represents one stored relationship.

- `@Entity` marks a JPA database model; `@Table` names the table and constraints.
- `@Id` and `@GeneratedValue` identify the generated primary key.
- `@ManyToOne` connects many like records to one account or one video.
- `@JoinColumn` identifies the column that stores the related record's ID.
- `LAZY` avoids automatically loading relationships whenever the entity is read.
- `Instant` represents an absolute moment in time.
- The protected empty constructor lets JPA create an object when reading records.

An entity is a class. The team's **DTO convention** uses records; that does not mean
JPA entities should also become records.

## 4. Define the response DTOs as records

In `dto/likedvideos`:

- `LikedVideoResponse(VideoSummaryDto video, Instant likedAt)` is one library item.
- `LikedVideoStatusResponse(Long videoId, boolean liked)` describes the button state.
- `LikedVideoRow(...)` is an internal query projection containing only the metadata
  needed to build the list response. It is not returned directly by the controller.

Records generate constructors, accessors, `equals`, `hashCode`, and `toString`. For
example, call `response.likedAt()` instead of `response.getLikedAt()`. They have no
setters. The video response reuses your teammate's `VideoSummaryDto` rather than
copying title/channel/thumbnail fields into a second public video format.

There is no Like request-body DTO: the video ID is already in the URL and the user ID
comes from the session. PUT and DELETE have no JSON body.

## 5. Let the repository handle database access

`repository/LikedVideoRepository.java` extends `JpaRepository<LikedVideoEntity, Long>`.
The type parameters describe the entity and its primary-key type.

The repository has four feature operations:

1. `insertIfAbsent`: native SQL inserts a relationship. `ON CONFLICT DO NOTHING`
   leaves an existing relationship unchanged. `@Modifying` marks a write query.
2. `deleteForUserAndVideo`: removes only the row matching both IDs.
3. `existsByUser_UserIdAndVideo_VideoId`: Spring Data derives an existence query
   from the method name. Underscores explicitly traverse the related entities.
4. `findVisibleLikesByUserId`: JPQL selects `LikedVideoRow` records and applies the
   user and privacy filters before pagination. JPQL refers to Java entity properties;
   native SQL refers to database table and column names.

The list query deliberately projects metadata. Loading full `VideoEntity` objects
would also load potentially huge video byte arrays merely to draw video cards.
We calculate whether a thumbnail exists in SQL, rather than downloading its bytes.

## 6. Put the rules in the service

`service/likedvideos/LikedVideoService.java` receives its dependencies through its
constructor. Spring supplies the repositories and the team's `Clock` bean. This is
constructor injection; there is no need to manually create these objects with `new`.

- `likeVideo`: require an existing account, validate the video ID, read the video's
  access metadata, enforce private-video ownership, and insert using `clock.instant()`.
- `unlikeVideo`: require the account and valid ID, then delete that account's like.
  It does not demand the video remain visible just to allow removal.
- `getLikeStatus`: require account and visible video, then return the existence result.
- `getLikedVideos`: validate paging, retrieve one metadata page, convert each row to
  `VideoSummaryDto`, and wrap it in `LikedVideoResponse` with the stored time.

`@Transactional` groups work in a database transaction. Writes commit on success and
roll back on runtime failure. `@Transactional(readOnly = true)` marks the reads.
The injected Clock makes time replaceable in tests. Data and access decisions stay
on the server; changing a React button cannot grant access to private content.

## 7. Expose HTTP endpoints through the controller

`controller/LikedVideoController.java` handles HTTP input and delegates to the service.
`@RestController` returns data as JSON. `@RequestMapping` supplies the common URL prefix.
`CurrentUser.require(session)` gets the ID from the server-side session or returns 401.

| Method | Endpoint | Result |
| --- | --- | --- |
| GET | `/api/liked-videos?page=0&size=20` | 200, JSON array of library items |
| GET | `/api/liked-videos/25` | 200, `{"videoId":25,"liked":true}` or false |
| PUT | `/api/liked-videos/25` | 204, no body; like video 25 |
| DELETE | `/api/liked-videos/25` | 204, no body; unlike video 25 |

PUT is used because setting "this video is liked" is idempotent: repeating the request
does not create extra likes. DELETE is also idempotent. A toggle endpoint would make
network retries ambiguous, so the two operations are explicit.

`@Positive` validates video IDs. Page numbers start at zero; size defaults to 20 and
must be 1 to 100. Missing sessions/accounts produce 401, invalid parameters produce
400, and missing or inaccessible private videos produce 404 for Like/status. Empty
lists return `[]`. An absent like can still be deleted successfully.

GET returns one page as an array, not a total count. An empty or short page means
the end. If there are exactly 20 entries, one additional Next request may return no
entries; the UI returns to the prior page. Inserts/deletes between requests can shift
offset-based page boundaries. Cursor pagination can be a later improvement.

## 8. Connect React to the API

`frontend/src/api/likedVideos.js` centralizes the four requests. It sends
`credentials: 'include'` so the session cookie travels with requests and turns server
errors into displayable messages. It never supplies a hardcoded user ID.

`components/LikedVideos/LikeButton.jsx` loads the saved status when a watch page opens.
It uses `aria-pressed` to describe the toggle state, prevents clicks while loading or
saving, and changes the displayed state only after success. A failed save keeps the
old state and offers a retry that reloads the server state. WatchPage keys the button
by video and session so requests from a previous video/account cannot update the new
button. Effect cleanup aborts obsolete GET requests.

`pages/LikedVideos.jsx` displays real video cards, like times, refresh/retry controls,
empty/sign-in states, unlike actions, and page navigation. Removing the last entry on
a later page returns to the previous page. App remounts it when the signed-in account
changes. Aborted loads and completed requests from unmounted pages are ignored.

`App.jsx` and `Sidebar.jsx` add navigation and mobile access. The liked-video card
passes its existing metadata to the watch route, so a previously liked unlisted video
does not depend on being present in the public feed. Its player still calls the team's
playback-authorisation endpoint. Liking a locked members-only video does not unlock it.

## 9. Follow one click through the system

```text
Click Like on video 25
  -> LikeButton calls likeVideo(25)
  -> PUT /api/liked-videos/25, with session cookie
  -> Controller reads the signed-in account ID
  -> Service checks account, video, and visibility
  -> Repository inserts unless the user/video pair already exists
  -> PostgreSQL commits
  -> HTTP 204
  -> Button changes to Liked
```

Opening Liked videos sends a GET request instead. The repository selects metadata,
the service builds response records, and React renders the returned cards.

## 10. Run and verify it yourself

Follow the root README for infrastructure. On Windows the team's launcher is
`.\dev.cmd` from the project root. Open `http://localhost:3000`, start a development
session through the existing header, and choose an uploaded video. Click Like, open
Liked videos from the sidebar, then unlike it and return to the watch page. Refresh
the page to verify that state comes back from the database.

For Postman: start the dev session with `POST http://localhost:8080/api/session/dev`
and keep Postman's returned session cookie. Use the four endpoints above with a real
video ID and no request body. GET without the cookie should return 401.

Tests are in `backend/src/test/java/ITubeBackend/LikedVideoTests.java` and the frontend
LikeButton/LikedVideos test files. Backend tests exercise the real service/repository
and database, with MockMvc checking the HTTP controller inside the application. The
MockHttpSession used by controller tests avoids requiring Redis for those tests.
Tests roll back their fixtures; they do not seed production data. Frontend tests mock
HTTP responses and verify UI behavior, including errors and request cancellation.

```powershell
# From backend
.\mvnw.cmd test
# From frontend
npm test -- --run
npm run build
```

There is no public/global like count, dislike feature, Watch later, or playlist support
in this feature. Those are separate requirements. The current user identity mechanism
is the team's development session until the authentication developer replaces it.

## Verification performed for this implementation

- Full backend suite: 81 tests passed with H2 for integration fixtures.
- LikedVideoTests: all 15 tests also passed against an isolated PostgreSQL 17 database,
  overriding the test datasource and using SQL initialization plus Hibernate validation.
- PostgreSQL integrity checks: six concurrent conflict-safe inserts produced one like;
  an invalid video reference was rejected; account/video deletes cascaded to likes.
- Frontend: 28 tests passed, including navigating to Liked videos and opening an
  unlisted liked video that does not appear in the public feed. Production build passed.

The PostgreSQL checks used a disposable local container, which was removed afterward.
Controller tests use MockMvc and frontend tests simulate HTTP; a live browser session
through Redis and the full infrastructure stack was not exercised by those tests.
